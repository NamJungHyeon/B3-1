## 1. 네트워크 — VPC, 서브넷, IGW, 라우트 테이블

먼저 네트워크입니다.

VPC `10.0.0.0/16`을 만들고, 그 안에 서브넷 `10.0.1.0/24`를 하나 만들었습니다. 이 서브넷은 EC2가 뜰 때 퍼블릭 IP를 자동으로 받도록 설정했습니다.

VPC는 만들기만 하면 바깥과 완전히 끊겨 있습니다. 그래서 인터넷 게이트웨이, IGW를 만들어서 VPC에 붙였고요. 라우트 테이블을 따로 만들어 `0.0.0.0/0 → IGW` 경로를 넣고, 그 테이블을 제 서브넷에 연결했습니다.

**Q. VPC, Public Subnet, IGW, Route Table(0.0.0.0/0 → IGW)이 구성되어 있나요?**

네, 구성되어 있었습니다.

📖 README 3장 "구성 요소" 표

🖥️ `logs/tagpolicy-run.log` 4·5절

4절 생성 결과에 VPC `vpc-05713bf5c6a23b20e`, 서브넷, IGW `igw-064e41dcc91822d1d`, 라우트 테이블과 서브넷 연결 ID까지 실제 ID가 다 찍혀 있고요. 5절 검증에서 `PASS 0.0.0.0/0 -> igw-064e41dcc91822d1d`, 즉 라우트 테이블의 기본 경로가 바로 그 IGW로 간다는 게 확인됩니다.

🖥️ `screenshots/verify-aws-cloudshell.jpg` (이전 배포 당시 기록)

같은 스크립트로 먼저 배포했을 때의 CloudShell 화면인데, 라우트 테이블이 `local`과 `0.0.0.0/0 → igw` 두 줄이고 둘 다 `active`인 게 표로 보입니다. ID는 다르지만 구조는 똑같습니다.

**Q. 퍼블릭 서브넷 라우트 테이블에 0.0.0.0/0 → IGW가 왜 필요한가요?**

제가 이번에 이해한 건, "퍼블릭 서브넷"이라는 설정이 따로 있는 게 아니라는 점이에요. **라우트 테이블에 IGW로 가는 경로가 있는 서브넷을 퍼블릭 서브넷이라고 부르는 것**입니다.

라우트 테이블에는 기본적으로 VPC 내부로 가는 `local` 경로 하나만 있어요. 그래서 이 경로가 없으면 EC2에서 인터넷 쪽으로 나가는 패킷이 갈 곳이 없습니다.

중요한 건 **응답도 이 길로 나간다**는 점입니다. 요청이 IGW로 잘 들어와도 응답이 나갈 경로가 없으면 연결이 안 됩니다. `0.0.0.0/0`은 "VPC 안이 아닌 모든 주소"라는 뜻이에요. 사용자가 인터넷 어디서 접속할지 모르니까 기본 경로로 둡니다.

그리고 경로를 넣은 테이블을 서브넷에 연결하지 않으면 main 테이블이 대신 적용돼서 똑같이 안 됩니다. 그래서 "경로 추가"와 "서브넷 연결"을 둘 다 했습니다.

## 2. 서버 — EC2와 Nginx

다음은 서버입니다.

EC2는 Amazon Linux 2023, `t3.micro`, gp3 8GiB로 띄웠습니다. Nginx 설치는 SSH로 들어가서 손으로 하지 않고, user-data 스크립트로 처음 부팅할 때 자동으로 되게 했습니다.

🖥️ `infra/user-data.sh`

여기서 하는 일은 세 가지예요. Nginx를 설치하고, `/`에는 "Hello Cloud - B3-1" 페이지를 만들고, `/health`는 항상 `200 OK`를 돌려주게 설정합니다.

SSH 키는 제 Mac에서 직접 만들고, AWS에는 **공개키만** 등록했습니다. AWS가 키를 만들게 하면 개인키를 받아서 어딘가 저장하는 과정이 생기는데, 이렇게 하면 개인키가 제 Mac 밖으로 한 번도 안 나갑니다.

**Q. EC2에 SSH로 접속 가능하고, 웹 서버가 실행 중인가요?**

## 3. 방화벽 — 보안 그룹

보안 그룹 인바운드 규칙은 딱 두 줄입니다.

- **80번 포트는 전체 공개(`0.0.0.0/0`)** 입니다. 웹 서비스니까 누구나 들어와야 해서요.
- **22번 포트는 제 Mac의 공인 IP 하나(`/32`)만** 허용했습니다. SSH는 관리자인 저만 쓰니까요.

여기서 하나 신경 쓴 게 있는데요. 저는 리소스를 CloudShell에서 만들었는데, 스크립트가 IP를 자동으로 잡으면 CloudShell의 IP가 들어갑니다. 그런데 실제로 SSH를 할 곳은 제 Mac이잖아요. 그래서 `SSH_IP` 옵션을 만들어서 Mac의 IP를 직접 넘겼습니다.

**Q. 인바운드가 필요한 포트만 허용하고, SSH가 특정 IP로 제한되어 있나요?**

네.

📖 README 4장 첫 표

🖥️ `logs/tagpolicy-run.log` 5절

검증 스크립트가 실제 보안 그룹을 조회해서 `PASS 전체 포트 0.0.0.0/0 규칙 없음`, `PASS SSH 소스가 /32 단일 IP (121.135.181.35/32)`를 냈습니다.

🖥️ `screenshots/verify-aws-cloudshell.jpg` (이전 배포 당시 기록)

규칙 표를 그대로 보시면 `80 0.0.0.0/0`, `22 121.135.181.35/32` 이 두 줄만 있습니다. 같은 스크립트라 규칙도 같습니다.

**Q. 어떤 기준으로 보안 그룹을 최소화했나요? 연 포트와 안 연 포트는요?**

기준은 두 가지였습니다. **"이 서버가 하는 일에 꼭 필요한 포트인가"**, 그리고 **"그 포트를 누가 써야 하는가"**요.

서비스가 HTTP 하나라서 80만 열었고, 관리용 22는 열되 저 한 명으로 좁혔습니다.

안 연 것도 이유가 있어요. 443은 인증서를 안 붙였으니 열 필요가 없었고, DB 포트는 이 서버에 DB가 없어서 닫았습니다. ping, ICMP도 미션에 필요 없어서 안 열었습니다.

보안 그룹은 기본이 전부 차단이고 허용만 추가하는 구조라서, "뭘 막을까"가 아니라 **"뭘 꼭 열어야 하나"**로 생각했습니다. 아웃바운드는 기본값인 전체 허용을 유지했는데, Nginx 패키지 설치하고 바깥 연결을 검증할 때 필요했기 때문입니다.

**Q. SSH나 DB 포트를 0.0.0.0/0으로 열면 안 되는 이유와 대안은요?**

퍼블릭 IP가 생기는 순간부터 인터넷의 자동 스캐너들이 계속 두드립니다. 22번이 다 열려 있으면 비밀번호 무차별 대입이나 SSH 취약점 공격 대상이 되고, DB 포트가 열려 있으면 데이터가 바로 노출됩니다. 키 인증을 써도 굳이 공격받을 문을 열어 둘 이유가 없습니다.

대안은 네 가지 정도 생각했습니다.

1. **이번에 쓴 방법은 제 IP `/32`로만 여는 것입니다.** 대신 IP가 바뀌면 규칙을 고쳐야 하는 불편이 있는데, 이건 뒤의 트러블슈팅에서 실제로 재현해 봤습니다.
2. **SSM Session Manager를 쓰면 22번을 아예 닫을 수 있습니다.** IAM 권한으로 접속하고 기록도 남습니다.
3. **Bastion 서버나 VPN으로 관리 경로를 하나로 모으는 방법**도 있습니다.
4. **DB는 프라이빗 서브넷에 두고**, 보안 그룹의 소스를 IP가 아니라 "웹 서버의 보안 그룹"으로 지정합니다. 그러면 웹 서버만 DB에 붙을 수 있습니다.

## 4. 권한 — IAM 최소 권한

다음은 IAM입니다. 이 부분에서 고민을 제일 많이 했어요.

리소스를 루트 계정으로 만들지 않으려고 `b3-1-operator`라는 IAM 사용자를 만들었고, 제가 직접 쓴 정책 하나만 붙였습니다. AdministratorAccess는 안 붙였습니다.

📖 README 4장 "IAM 정책"

🖥️ `infra/iam-policy.json`

정책을 짤 때 걸린 게 하나 있었어요. 이 AWS 계정에는 이미 다른 프로젝트인 FireView 서버가 돌고 있었습니다. "서울 리전에서 EC2, VPC 작업만 허용" 정도로는 이 운영 사용자가 그 서버까지 끌 수 있습니다.

그래서 정책을 **태그 기준**으로 짰습니다.

- 만들 때는 `Project=B3-1` 태그를 붙여야만 만들 수 있습니다.
- 수정, 연결, 삭제는 `Project=B3-1` 태그가 붙은 리소스에만 됩니다.
- 태그는 만드는 순간에만 붙일 수 있습니다. 나중에 FireView 서버에 B3-1 태그를 붙여서 우회하는 걸 막으려고요.
- 인스턴스는 micro 타입만 띄울 수 있습니다.

**Q. 보안 그룹과 IAM은 책임 범위가 어떻게 다르고, 최소 권한은 왜 필요한가요?**

둘은 막는 대상이 다릅니다.

- **보안 그룹은 네트워크 패킷을 막습니다.** "어느 IP에서 이 서버 몇 번 포트로 들어올 수 있나"를 정하고, 인터넷 사용자를 통제합니다.
- **IAM은 AWS API 호출을 막습니다.** "누가 서버를 만들고 지우고, 보안 그룹 규칙을 바꿀 수 있나"를 정하고, AWS를 조작하는 사람과 프로그램을 통제합니다.
- **SSH 키**는 그 위에서 "서버 OS에 로그인할 수 있나"를 정하는 또 하나의 층입니다.

보안 그룹을 아무리 잘 잠가도, IAM 권한이 넓으면 누가 API로 그 규칙을 `0.0.0.0/0`으로 바꿔버릴 수 있어요. 그래서 둘 다 필요합니다.

최소 권한이 필요한 이유는 **사고가 났을 때 피해 범위를 줄이기 위해서**입니다. 키는 유출될 수 있고 사람은 실수로 엉뚱한 ID를 지울 수 있어요. 제 경우가 딱 그 예시였습니다. 리전 조건만 있었다면 정리 스크립트에서 실수 하나로 다른 프로젝트 서버가 꺼질 수 있었습니다.

🖥️ `screenshots/tagpolicy-dryrun.jpg`, `logs/tagpolicy-run.log` 1·5절

그래서 정책을 `--dry-run`으로 직접 확인했습니다. dry-run은 실제로 실행하지 않고 권한만 확인하는 옵션입니다.

- FireView 서버를 종료, 중지, 재부팅하거나 FireView에 태그를 붙이려고 하면 전부 **거부**됐습니다.
- B3-1 서버에 대한 종료와 재부팅은 **허용**으로 나왔습니다.
- 태그 없이 VPC를 만들면 거부, 태그를 붙이면 허용이었습니다.

🖥️ `logs/iam-least-privilege.log` (이전 배포 당시 기록)

관련 없는 서비스도 확인했습니다. 이 사용자로 S3 버킷 목록, RDS 조회, IAM 사용자 목록을 부르면 전부 `AccessDenied`입니다.

**Q. 권한이 부족해서 작업이 실패하면, 권한을 무작정 올리지 않고 어떻게 최소 범위를 찾나요?**

이건 실제로 겪은 일로 말씀드릴게요.

배포 첫 시도가 중간에 멈춰서 정리 스크립트를 돌렸는데, 키페어를 지우려다 **권한 없음** 에러가 났습니다. 제일 쉬운 해결은 키페어 삭제 권한을 조건 없이 주거나 Admin을 붙이는 거였는데, 그렇게 안 했습니다.

1. 먼저 **에러 메시지를 정확히 읽었습니다.** 막힌 액션은 `DeleteKeyPair`였는데, 대상 리소스가 특정 키페어가 아니라 `*/*`로 나와 있었어요.
2. **정책에 그 액션이 있는지 확인했더니, 있었습니다.** 다만 "B3-1 태그가 붙은 것만"이라는 조건이 걸려 있었어요.
3. 그래서 **"조건이 왜 안 맞았을까"라는 가설**을 세웠습니다. 앞 단계에서 공개키 파일이 사라져서 키페어가 아예 안 만들어졌던 거예요. 없는 리소스에는 태그도 없으니 조건을 만족할 수가 없죠.
4. **비교로 확인했습니다.** 공개키를 홈 디렉터리에 두고 다시 배포했더니, 같은 정책으로 키페어 삭제가 정상적으로 성공했습니다. 그래서 권한이 빠진 게 아니라는 결론을 냈습니다.

일반화하면 이렇습니다.

- 실패한 액션과 리소스를 특정합니다.
- 그 액션 하나만, 리전·ARN·태그로 범위를 좁혀서 추가합니다.
- dry-run으로 허용되는지, 그리고 **다른 리소스에는 여전히 막히는지**까지 확인합니다.

필요하면 `decode-authorization-message`로 인코딩된 거부 사유를 풀어볼 수도 있고, CloudTrail에서 실제로 쓴 액션만 뽑아서 정책을 좁히는 방법도 있습니다. 이번에는 비교로 결론이 나서 디코딩까지는 안 했습니다.

솔직하게 말씀드리면 한계도 있습니다.

- 조회 권한은 아직 리전 전체를 볼 수 있습니다.
- 누구든 B3-1 태그만 붙이면 새 리소스를 만들 수 있습니다.
- IAM 사용자를 만드는 것과 Billing 확인은 루트로 했습니다.

이 부분은 README 4장 "루트 계정 사용 범위"와 9장 "한계"에 그대로 적어 뒀습니다.

## 5. 외부 접속 검증 — (B) /health

**Q. 외부 접속을 어떤 방식으로 검증했나요?**

저는 **(B) `/health` 방식**으로 했습니다.

📖 README 6장 첫 표

🖥️ `logs/tagpolicy-verify-local.log`, `logs/tagpolicy-run.log` 5절

제 Mac과 CloudShell, 서로 다른 두 곳에서 `http://43.201.55.219/health`를 호출해서 둘 다 PASS였습니다. Mac 쪽은 12시 33분 16초(KST)에 `HTTP/1.1 200 OK`와 본문 `OK`가 원문 그대로 찍혀 있습니다.

🖥️ `screenshots/browser-root.jpg`, `browser-health.jpg` (이전 배포 당시 기록)

보조로 (A) 브라우저 접속도 했습니다. 다만 캡처에 주소창이 안 나와서 주 증빙은 B로 잡았습니다.

**Q. 왜 B를 골랐고, 그걸 위해 뭘 구성했나요?**

B를 고른 이유는 **사람 눈이 아니라 스크립트가 판정할 수 있어서**입니다. 브라우저는 제가 화면을 봐야 하지만, `/health`는 상태 코드 200과 `OK`라는 고정 문자열로 바로 PASS/FAIL을 낼 수 있어요. 그래서 검증 스크립트에 그대로 넣었습니다. 나중에 로드 밸런서를 붙이면 헬스 체크 경로로 그대로 쓸 수 있다는 것도 장점이었습니다.

구성은 세 가지를 했습니다.

1. **Nginx 설정입니다.** `location = /health { return 200 "OK"; }`를 넣었습니다. 파일을 읽지 않고 Nginx가 바로 응답하니까 "Nginx가 살아 있다"만 순수하게 확인할 수 있습니다.
2. **네트워크입니다.** 보안 그룹 80번 공개, 라우트 테이블 IGW 경로, 퍼블릭 IP 자동 할당입니다.
3. **검증 스크립트입니다.** 외부에서 `/health`를 부르는 것과 SSH로 들어가 `localhost`를 부르는 것을 따로 확인했습니다. 안에서 되는 것만으로는 밖에서 된다는 증거가 안 되니까요.

## 6. 트러블슈팅

트러블슈팅은 미션 형식대로 **증상 → 가설 → 검증 → 조치 → 결과 → 재발방지** 순서로 세 건 썼습니다.

📖 README 6장 "증빙 파일 목록"

🖥️ `docs/troubleshooting.md`

- **1번은 외부 HTTP 타임아웃입니다.** 실제로 재현하지는 않았고, 점검 절차를 정리한 예상 시나리오입니다.
- **2번은 SSH 타임아웃입니다.** 이전 배포 때 일부러 재현해서 고친 실제 기록입니다.
- **3번은 앞에서 말씀드린 키페어 권한 에러입니다.** 실제로 겪은 기록입니다.

2번을 짧게 말씀드리면 이렇습니다.

- **증상:** 보안 그룹의 SSH 허용 IP를 일부러 다른 IP로 바꿔서 "내 IP가 바뀌었는데 규칙은 옛날 IP인 상황"을 만들었습니다. 그러니까 SSH가 타임아웃이 났습니다.
- **가설:** "허용 IP와 제 실제 IP가 안 맞는다"였습니다.
- **검증:** 제 IP를 확인했고, 같은 순간에 80번은 연결되고 22번만 안 되는 걸 확인했습니다.
- **조치:** 옛 규칙을 지우고 제 IP `/32`를 다시 넣었습니다.
- **결과:** SSH, Nginx, localhost가 전부 정상으로 돌아왔습니다.

🖥️ `logs/ts-ssh-break.log` → `symptom` → `fix` → `result` 순서로

**Q. 가설 → 검증 순서를 지킨 이유와 로그를 어떻게 활용했나요?**

가설 없이 바로 손대면 "되긴 됐는데 왜 됐는지 모르는" 상태가 됩니다. 최악은 SSH가 안 된다고 22번을 전체에 열어버리는 거예요. 접속은 되지만 원인은 모르고 보안만 망가지죠.

가설을 먼저 세우면 **뭘 확인하면 맞는지 틀린지가 정해지고**, 조치도 그 원인 하나에만 들어갑니다.

이번에 핵심 근거는 **"80은 되는데 22만 안 된다"는 비교**였습니다. 이 하나로 여러 원인을 지울 수 있었어요.

- 서버가 죽었거나 라우팅 문제였다면 80도 안 됐어야 합니다.
- 키 인증 실패는 연결이 된 다음에 나는 에러라서, 타임아웃과는 모양이 다릅니다.

로그는 단계별로 파일을 나눠서 **조치 전과 후를 비교할 수 있게** 남겼습니다.

로그를 읽을 때 조심한 것도 있어요. 증상 로그에 `exit=0`이 찍혀 있는데, 이건 SSH 결과가 아니라 파이프 끝의 `tail` 명령의 종료 코드라서 성공 근거로 안 썼습니다. 1번 사례는 재현을 안 했으니 "고쳤다"고 쓰지 않았고요. **근거 없는 건 안 쓴다**가 원칙이었습니다.

**Q. 외부 접속이 안 되면 어떤 순서로 점검하나요?**

**패킷이 지나가는 순서대로, 바깥에서 안쪽으로** 봅니다.

1. **에러 모양부터 구분합니다.** `curl -v`로 보면 됩니다.
   - **타임아웃**이면 중간에서 패킷이 버려진 거라서 라우팅이나 보안 그룹 쪽입니다.
   - **Connection refused**면 서버까지는 갔는데 80번에 듣는 프로세스가 없는 거라서 Nginx 쪽입니다.
   - **5xx**면 Nginx 설정이나 앱 문제입니다.
2. **라우팅을 봅니다.** 서브넷에 실제로 연결된 라우트 테이블에 IGW 경로가 `active`인지, IGW가 이 VPC에 붙어 있는지 확인합니다.
3. **보안 그룹을 봅니다.** 80번이 열려 있는지, 그 보안 그룹이 실제로 이 인스턴스에 붙어 있는지 확인합니다.
4. **퍼블릭 IP와 DNS를 봅니다.** 제가 부른 IP가 지금 IP가 맞는지 확인합니다. 자동 IP는 서버를 껐다 켜면 바뀝니다. 도메인을 쓰면 DNS가 그 IP를 가리키는지도 봅니다.
5. **마지막으로 SSH로 들어가 서버를 봅니다.**
   - `curl localhost/health`를 불러봅니다. 안에서 되면 문제는 바깥쪽입니다.
   - `systemctl status nginx`, `nginx -t`, 에러 로그를 봅니다.
   - 막 부팅했다면 user-data가 끝났는지 cloud-init 로그를 봅니다.
   - access 로그에 제 요청이 **아예 없다**면 네트워크에서 막힌 겁니다.

## 7. 리소스 추적과 정리

마지막으로 정리입니다. 실습 끝나고 안 지우면 돈이 나가니까요.

정리 스크립트는 **만든 순서의 반대로** 지웁니다. EC2 종료부터 하고 끝날 때까지 기다린 다음 EIP, EBS, 보안 그룹, 라우트 테이블, 서브넷, IGW, VPC, 키페어 순서입니다.

반대로 지우는 이유는 의존 관계 때문입니다.

- EC2가 보안 그룹과 서브넷을 붙잡고 있어서, EC2가 먼저 사라져야 나머지를 지울 수 있습니다.
- IGW는 VPC에서 떼어내야 지워지고, VPC는 안이 비어야 지워집니다.

**Q. 체크리스트에서 EC2/EBS/EIP/IGW/VPC 5종 정리를 확인할 수 있나요?**

네.

📖 README 7장 "정리 결과"

🖥️ `docs/cleanup-checklist.md`, `logs/tagpolicy-run.log` 6절, `screenshots/tagpolicy-cleanup.jpg`

스크립트의 "완료" 문구만 믿지 않고, **지운 다음 다시 조회한 결과**로 체크했습니다. 마지막 재조회는 12시 34분 48초(KST)입니다.

| 리소스 | 다시 조회한 결과 |
| --- | --- |
| EC2 | `terminated` |
| EBS | 인스턴스와 같이 삭제됐고, B3-1 볼륨 0개 |
| EIP | 이번 배포는 EIP를 안 쓰고 자동 퍼블릭 IP를 썼습니다. B3-1 EIP 0개 |
| IGW | 분리 후 삭제, 0개 |
| VPC | 조회하면 `InvalidVpcID.NotFound` |

그 외에 보안 그룹, 라우트 테이블, 서브넷, 키페어도 지웠고 키페어는 조회하면 `InvalidKeyPair.NotFound`입니다. IAM 사용자의 액세스 키도 루트로 지워서 남은 키가 0개입니다. 제 Mac과 CloudShell에 있던 SSH 키 파일도 지웠습니다.

**Q. 리소스를 추적하고 정리하는 데 어떤 기준을 썼나요?**

세 가지를 겹쳐서 썼습니다.

1. **태그 `Project=B3-1`.** 모든 리소스에 만들 때 붙였고, 정리 후에 이 태그로 조회해서 "하나도 안 남았다"를 확인했습니다.
   이 태그는 단순한 메모가 아니라 **IAM 정책의 경계**이기도 합니다.
   제 계정에는 FireView 리소스가 섞여 있었어요. 정리 조회 때 FireView의 DB와 EIP가 보였는데, 태그가 없어서 제 것이 아닌 걸 바로 구분했고 건드리지 않았습니다.
2. **이름 규칙 `b3-1-*`.** `b3-1-vpc`, `b3-1-igw`, `b3-1-web-sg`처럼 지어서 콘솔 목록에서 눈으로 바로 알아볼 수 있게 했습니다.
3. **상태 파일과 체크리스트.** 만들 때 ID를 상태 파일에 적어 두고, 정리 스크립트는 그 ID만 정확히 지웁니다.
   상태 파일이 이미 있으면 생성 스크립트가 멈춰요. 그래서 정리 안 하고 실수로 두 벌 만드는 일도 막습니다.
   마지막으로 체크리스트에 "지움 → 다시 조회한 결과"를 항목별로 적었습니다.

## 8. 비용 — Billing

🖥️ `screenshots/billing-summary.jpg`, `billing-services.jpg`

📖 README 7장 "Billing 확인"

Billing 청구서에서 11월 예상 금액 **0.00달러**를 확인했습니다. 다만 이건 무료 플랜 크레딧으로 처리된 금액이라 B3-1만 따로 계산한 금액은 아닙니다. 그리고 이 캡처는 오전 10시 15분에 찍어서, 12시 반에 검증한 배포의 사용분은 반영되지 않았습니다. 사용량은 반영이 늦을 수 있어서 다시 확인이 필요합니다.

**Q. Billing에 예상 못 한 비용이 찍히면 뭐부터 의심하고 어떻게 추적하나요?**

**켜두면 시간당 돈이 나가는데 눈에 잘 안 띄는 것**부터 의심합니다.

1. **안 끈 EC2입니다.** 특히 다른 리전에 실수로 만든 것이요.
2. **퍼블릭 IPv4와 Elastic IP입니다.** 퍼블릭 IPv4는 이제 시간당 과금되고, 서버에 안 붙은 EIP도 돈이 나갑니다. 실제로 제 계정에도 FireView의 EIP가 하나 있어서, 비용이 찍히면 제일 먼저 볼 후보입니다.
3. **혼자 남은 EBS 볼륨과 스냅샷입니다.** EC2를 지워도 볼륨은 설정에 따라 남을 수 있습니다.
4. **NAT Gateway, 로드 밸런서, RDS입니다.** 켜져 있기만 해도 비쌉니다. 제 계정엔 FireView의 RDS도 있습니다.
5. **바깥으로 나가는 데이터 전송 비용입니다.**

추적은 이렇게 합니다.

- Billing에서 **청구서 → 서비스별 → 리전별**로 내려가서 범위를 좁힙니다.
- **Cost Explorer**에서 하루 단위, 사용 유형별로 봅니다. 그러면 "퍼블릭 IP 사용 시간", "gp3 볼륨 사용량" 식으로 뭐가 언제부터 나갔는지 보입니다.
- 비용 배분 태그로 `Project`를 켜 두면 프로젝트별로도 볼 수 있습니다. 태그를 붙여둔 게 여기서도 도움이 됩니다.
- 리소스는 **Tag Editor나 Resource Explorer로 모든 리전을 한 번에** 검색합니다. 콘솔은 리전별로만 보여줘서 놓치기 쉽거든요.

찾으면 태그와 이름으로 제 것인지 먼저 확인하고, 의존 순서대로 지우고 다시 조회합니다. 제 것이 아니면 함부로 안 지우고 주인에게 물어봅니다. 이번에 FireView를 안 건드린 것과 같은 원칙입니다.

예방책으로는 AWS Budgets에 1달러 정도 알림을 걸어 두고, 실습 끝나면 바로 정리 스크립트를 돌리는 걸 습관으로 하려고 합니다.

## 9. 다이어그램으로 마무리 — 흐름, 그리고 확장

📖 README 3장 "요청이 서버까지 가는 길"

🖥️ `docs/architecture.png` (그림 속 ID와 IP는 이전 배포 값, 구조는 같음)

**Q. 외부 → IGW → Subnet → EC2 흐름을 다이어그램으로 설명해 주세요.**

다이어그램의 **파란 선**을 왼쪽에서 오른쪽으로 따라가 보시면 됩니다. 주황 선은 같은 길로 들어오는 제 SSH이고, 점선은 라우트 테이블이나 IAM 같은 설정입니다.

1. 왼쪽 **Internet / Users**에서 사용자가 `http://퍼블릭IP/health`를 요청합니다.
2. **Internet Gateway**에 도착합니다. VPC의 출입문이고, 퍼블릭 IP를 EC2의 내부 IP(`10.0.1.x`)로 바꿔서 안으로 넘깁니다.
3. **Public Subnet** 안으로 들어갑니다. 이 서브넷이 퍼블릭인 이유는 아래 **Route Table**에 `0.0.0.0/0 → IGW`가 있어서입니다.
4. **Security Group**이 검사합니다. 80번이고 전체 허용이라 통과합니다. SSH였으면 제 IP인지를 검사했겠죠.
5. **EC2의 Nginx**가 `/health` 규칙대로 `200 OK`를 만듭니다.
6. 응답은 라우트 테이블의 IGW 경로를 타고 나가고, IGW가 다시 퍼블릭 IP로 바꿔서 인터넷으로 보냅니다. 보안 그룹은 들어온 요청의 응답을 자동으로 내보내 주기 때문에, 아웃바운드 규칙을 따로 안 열어도 됩니다.

이 중 하나만 빠져도 접속이 안 되고, 그래서 이 순서가 그대로 아까 말씀드린 점검 순서가 됩니다.

**Q. 트래픽이 늘어서 인스턴스를 2대로 늘려야 하면, 지금 구조에서 뭐가 병목이고 뭘 추가하나요?**

지금 구조의 문제는 **"전부 하나"**라는 점입니다.

- **입구가 EC2 한 대의 퍼블릭 IP입니다.** 서버를 두 대로 늘려도 사용자는 IP 하나만 알아서 트래픽을 나눠 줄 게 없습니다. 그 IP도 재시작하면 바뀌고요.
- **서버 하나, AZ 하나, 서브넷 하나라서**, 그 서버나 그 AZ가 죽으면 서비스 전체가 멈춥니다.
- **`t3.micro`는 버스트형이라** 부하가 계속되면 CPU 크레딧이 떨어져 느려집니다.
- **서버를 늘릴수록 손으로 만드는 방식 자체가 병목**이 됩니다.

그래서 추가할 건 다음과 같습니다.

1. **다른 AZ에 퍼블릭 서브넷을 하나 더** 만듭니다. 로드 밸런서는 최소 2개 AZ가 필요하고, AZ 장애에도 버틸 수 있습니다.
2. **ALB를 붙입니다.** 단일 주소로 받아서 두 서버에 나눠 줍니다. 헬스 체크 경로로는 **이미 만든 `/health`를 그대로 쓰면 됩니다.** 응답 없는 서버는 자동으로 빠집니다. 아까 B 방식을 고른 이유가 여기서 이어집니다.
3. **보안 그룹을 바꿉니다.** ALB에서 80/443을 전체에 엽니다. EC2의 80번은 "전체"가 아니라 **ALB의 보안 그룹에서 온 것만** 받게 해서, 서버에 직접 접근하는 길을 막습니다.
4. **Auto Scaling Group을 씁니다.** 지금의 user-data를 Launch Template에 넣고, 최소 2대를 유지하면서 부하에 따라 늘리고 줄입니다.
5. 더 가면 **EC2를 프라이빗 서브넷으로** 옮기고 관리는 Session Manager로 하면 22번도 닫을 수 있습니다. 대신 NAT Gateway 비용은 따져봐야 합니다.

이 확장은 미션 보너스 항목이고, 이번 결과물에서는 실제로 구성하지 않았습니다. README 9장에도 미수행으로 적어 뒀습니다.

## 10. 마무리 멘트

정리하면,

- VPC부터 EC2까지 스크립트로 만들었고,
- `/health`로 외부 접속을 확인했고,
- 보안 그룹은 80 전체, 22는 제 IP만 열었고,
- IAM은 태그 조건으로 제 리소스만 건드릴 수 있게 좁혔고, 다른 프로젝트 서버는 거부되는 걸 dry-run으로 증명했고,
- 전부 지운 다음 다시 조회해서 남은 게 없는 걸 확인했습니다.

모든 주장은 `logs/`와 `screenshots/`에 근거가 있고, 안 한 건 안 했다고 적어 뒀습니다. 질문 있으시면 편하게 해주세요. 감사합니다.
